# Optional Input presence guard — proposed contract

Refs vanderpol/scap-ng#255, #268, #269; Decisions15/16.

On 2026-11-01 the owner approved **designing the explicit presence guard**:
provided empty counts as present, omission selects fallback, and uncertain
binding preserves error/unknown. This packet supplies that design for review.
It does not adopt a syntax, activate a schema, change compiler acceptance or
claim a working invocation/scanner. Current optional consumption stays rejected.

## Proposed minimal syntax and scope

Use `if: {input_provided: <local-input-id>}` as a dedicated conditional guard,
also permitted as a direct `else_if[].if`. Keep existing ordered `then`/final
`else`. The token names provision, not truthiness, nonemptiness or successful
collection. It references an existing local Input declaration; it cannot read
another Assessment's Input, declare a new binding or execute a Test/Variable.

For this first contract, do not permit the new atom in general Boolean trees,
standalone `evaluate`, `not`, Test predicates or applicability. Nested explicit
conditionals can guard several optional Inputs. Broader logical implication or
negated-presence reasoning is deferred. This confines static authorization to
positive branch dominance rather than assuming Boolean evaluation order.

The serialized `required` and `cardinality` remain mandatory and independent.
No new default, coalescing value, null sentinel or implicit cast is introduced.
Actual invocation wire syntax stays unchanged/unimplemented until its separate
binding adapter is qualified; the states below are an internal contract, not
invented YAML fields.

## Binding states and guard results

Resolve one immutable binding snapshot per invocation, retaining binding source
and diagnostics. The same Input cannot be omitted for one consumer and present
for another. An invocation that lacks a required Input is invalid regardless of
branch choice; do not use the guard to hide a mandatory contract violation.

| Binding observation | Guard result | Consequence |
| --- | --- | --- |
| Optional, definitively omitted | false | Only the authored fallback/next branch may run |
| Supplied nonempty, type/cardinality/constraints valid | true | Selected then branch may consume the values |
| Supplied `[]`, cardinality permits zero | true | Empty stays empty; ordinary field/array requirements determine its meaning |
| Supplied `false`, `0` or `''`, type/constraints valid | true | Never interpreted as omission |
| Supplied empty where cardinality forbids zero | error | Reason-bearing invalid binding; no fallback |
| Wrong datatype, invalid constraints, malformed binding or conflicting sources | error | No coercion, collector call or fallback |
| Provider cannot establish whether a binding was supplied | unknown | Preserve uncertainty and reason; no fallback |
| Provider/binding resolution fails | error | Preserve failure and reason; no fallback |
| Pending resolution | no final result | Resolve or terminate with explicit unknown/error; never treat pending as omitted |

Only true/false/error/unknown are generated by this guard. It does not generate
not_applicable/not_evaluated; those remain authored terminal/other technical
outcomes. Existing conditional six-state propagation remains unchanged.

## Compile-time closure and lazy execution

1. Resolve every Input/Test/Object/Variable/dependency reference in every branch,
   including unselected branches. Existing duplicate, type, cycle and resource
   limit checks still apply. A false guard cannot hide malformed source.
2. Compute each executable consumer's transitive optional-Input dependencies,
   including Object selectors, Set/Filter operands, Variables, comparisons and
   dependency invocation bindings. Opaque literal record data is not a reference.
3. Descending through the guard's true `then` adds that Input to the set known
   provided; false/fallback adds nothing. Enclosing positive guards persist into
   nested branches. An earlier false guard gives no authority to a later branch.
4. Every optional dependency must be positively guarded at **every reachable
   consumer occurrence**. One guarded use does not authorize an unguarded use of
   the same Test, shared Object or Variable elsewhere. Multiple optional Inputs
   require all relevant positive guards. A Test used to choose a branch cannot
   consume an optional Input that is only guarded within that branch.
5. Do not eagerly acquire or compute optional-dependent nodes before selection.
   Definitions remain static; execution follows the selected consumer closure.
   Cache identity includes invocation/binding identity and provided values;
   never reuse a result from another binding snapshot.
6. Compile a proposed `read_input_presence` instruction with the local Input ID
   and source path, plus an explicit Input reference set separate from Test and
   Assessment references. Independent package validation must reconstruct this
   from source, reject unknown instructions/IDs and compare the exact plan.

These are proposed obligations for a future implementation, not capabilities of
the current supplied-Test-result evaluator. Existing bytecode/source versions
must reject an unknown presence instruction. Do not silently reinterpret it as
a constant or supplied Test result; choose and record a versioned compiled
contract migration before shipping new packages.

## Small source-backed example and intentional change

The original-backed Server2025 SV-278080 example at source37b614858 compares
`windows.registry` NoLockScreenSlideshow DWORD with `value: {equals: 1}`. Its
source ZIP is pinned by SHA256
`2f46264b5fa21c8a033236121794ebe372314bf7458dac0aca4f81179fe7ece0`, NIWC library
revision8c8e5dff860af6b1290ee9273a282db24278f8d5; original content namespace is
DISA. See source `docs/examples/conformance-remediation-20261101/` and
`tests/fixtures/v04-direct-prototype/provenance.json`.

Before: the published fixture has a literal policy value and a direct Test
reference. It has no optional Input and remains unchanged/proved.

After, **intentional new authoring sketch, not an equivalent source migration**:
replace only the expected value with `{input: slideshow-value-input}`, retain
the complete field requirement/Object/reporting policy, and author:

```yaml
inputs:
  slideshow-value-input:
    datatype: integer
    cardinality: exactly_one
    required: false
evaluate:
  if: {input_provided: slideshow-value-input}
  then: {test: verifies-prevent-enabling-screen-slide-show-is-set-enabled-test}
  else:
    not_evaluated:
      reason: Organization has not supplied the expected slideshow policy value
```

The referenced Test's value predicate additionally uses `value_match: every`.
Supplying integer1 selects that comparison; omitting the Input selects the
explicit manual-follow-up reason. Providing an invalid empty list is error,
not omission. Selecting the Test and receiving false/error must retain that
outcome, not execute the fallback. A separate zero_or_more Input example covers
valid provided-empty presence; do not weaken this exactly_one example.

This deliberately delegates a policy operand and therefore is not a claim that
the original fixed DISA requirement permits tailoring it. Publish it only as a
new/differently identified requirement if used operationally; never modify the
original Rule, source proof or publisher Parameter under this example.

OVAL5.12.3 external_variable at pinned `oval-definitions-schema.xsd:551` models
external values and restrictions; it does not establish this native optional
Input guard. No OVAL equivalence, source defect or automatic conversion is
inferred from the proposed new syntax.

## Rejected alternatives

- Treat omitted as `[]`: loses Decision15's provided-empty distinction.
- Treat false/zero/empty string as omitted: confuses a valid value with provision.
- `has_value`: suggests nonemptiness and invites the same ambiguity.
- Generic `and`/`not` guard inference: requires broader six-state dominance and
  scheduling semantics; keep the first implementation deliberately explicit.
- Hidden fallback/default: changes policy without an authored branch/reason.
- Run guarded acquisition eagerly: still consumes the missing optional input.
- Prohibit all optional consumption: safe current behavior, but leaves the
  owner-approved useful optional pattern unavailable; retain only as fallback
  until the reviewed guard and binding scheduler are implemented.

## Required positive/negative implementation evidence

The adjacent design vectors are **expected review cases, not test results**.
Before enabling the candidate, require version-local schema/public/direct
compiler positives and negatives, transitive graph/dominance tests, immutable
binding/provenance tests, selected-only scheduling/caching tests, independently
decoded package instructions and supplied-binding traces for every table row.
Include a complete Rule manual-follow-up report with selected evidence/reason;
do not turn known failure into informational or assert scanner execution from
a supplied-result harness.

Run focused and affected maintained suites; reuse exact-head hosted results.
No65-stream regeneration, historical-proof hash change or new collector is
needed to review the design. Implementation activation and any compiled-format
change require owner review of this concrete packet. PR268 remains draft.
